## 1. 目的

本書は、SPLL公開ポータルからクラウドサインフォームへ遷移し、契約当事者情報を取得して利用許諾契約を締結するためのフォーム項目、入力規則、表示条件、hidden項目、契約書差込先、データ保存先及び証跡管理を定める。

フォーム設計の目的は、次のとおりである。

1. 契約当事者を正確に特定する
2. 公開ポータルで選択済みの原作及び利用条件を再入力させない
3. 個人・個人事業主・法人の差異を条件分岐で吸収する
4. 契約書への差込漏れ及び入力ゆれを防止する
5. SPLL台帳では不要な個人情報を保持しない
6. hidden値の改変を前提に、契約条件の真正性を検証できるようにする
7. CloudSign締結後の契約突合を`application_ref`で確実に行う

---

## 2. システム上の役割分担

### 2.1 SPLL公開ポータル

公開ポータルで確定する情報は次のとおりとする。

- 対象原作
- 利用目的
- 利用許諾条件及び料金条件
- 個人情報取扱通知の表示及び同意
- 利用規約の表示及び同意
- 申込参照番号の発行
- CloudSignフォームへの遷移

### 2.2 クラウドサインフォーム

クラウドサインフォームで取得する情報は次のとおりとする。

- 契約当事者の氏名又は法人名
- 住所及び連絡先
- 法人代表者又は契約締結権限者
- 屋号・サークル名
- 制作物及び頒布計画の概要
- 契約締結権限等の表明
- 電子署名に必要な情報

### 2.3 SPLL業務台帳

SPLL業務台帳では、原則として次の情報のみを保持する。

- `application_id`
- `application_ref`
- 対象原作
- 利用目的
- 契約条件スナップショット
- CloudSign書類ID
- 締結日時
- 締結済PDF及びハッシュ
- 契約、提出、請求、入金、清算等の業務状態

氏名、住所、電話番号、メールアドレス、銀行口座等の個人情報は、業務上必要な範囲を除き、SPLLのスプレッドシートへ複製しない。契約当事者情報の正本はCloudSign上の契約及び締結済PDFとする。

## 3. 基本フロー

```text
SPLL公開ポータル
  1. 原作選択
  2. 利用目的選択

  6. application_ref・handoff_token発行

 15. 契約登録・認証発行
```

## 4. 重要な設計原則

## 4.1 hidden項目を契約条件の正本としない

ブラウザのURLパラメータ又はhidden項目は、申込者が技術的に改変できることを前提とする。

したがって、次の値はCloudSignフォームの表示・差込に利用しても、SPLL上の契約登録及び請求条件確定時には信用しない。

- 原作ID
- 原作名
- 利用目的
- 料金
- 料率
- 支払条件
- 報告条件
- クレジット
- 特約

締結後は`application_ref`をキーとしてSPLL台帳上の申込スナップショットと照合する。

### 4.1.1 推奨する改変検知

公開ポータルから次の`handoff_token`を発行する。

```text
payload = application_id
        + application_ref
        + work_ids
        + usage_category
        + terms_snapshot_hash
        + expires_at

handoff_token = HMAC-SHA256(payload, HANDOFF_SECRET)
```

CloudSignフォームへは、`application_ref`、`handoff_token`及び表示用項目を渡す。

締結後に次を確認する。

- `application_ref`が存在する
- handoff tokenが有効である
- 有効期限内である
- 渡された条件のダイジェストが申込時スナップショットと一致する
- 締結済PDFに表示された条件が台帳のスナップショットと一致する

不一致の場合は契約を自動有効化せず、`link_status=TERMS_MISMATCH`として手動確認へ送る。

## 4.2 料金区分ごとのフォーム分割

hidden改変リスク及び契約書テンプレートの複雑化を抑えるため、可能であれば利用目的又は料金モデルごとにフォーム・契約書テンプレートを分ける。

推奨単位：

| フォーム | 主な利用目的 | 料金モデル |
|---|---|---|
| FORM-BOOK | 書籍 | PER_WORK |
| FORM-EBOOK | 電子出版物 | RATE |
| FORM-GOODS | 商品販売 | PER_WORK |
| FORM-SUBSCRIPTION | サブスクリプション | RATE |
| FORM-EVENT | イベント | FLAT又は無償 |
| FORM-OTHER | その他 | 個別確認 |

固定料金・料率及び主要条件を契約書テンプレート自体に固定し、hidden項目による差込を必要最小限にする。

フォーム分割が難しい場合は、単一フォーム内で利用目的を表示専用とし、締結後の条件照合を必須とする。

3. 審査・是正・取消しの確認
4. 報告・支払・反社等の契約上の義務の確認

# 7. hidden項目設計

## 7.1 必須hidden項目

| 正規キー | 内容 | 生成元 | 契約差込 | 締結後検証 |

| application_id | 申込ID | SPLL | 原則非表示 | ○ |
| handoff_token | 改変検知トークン | SPLL | 非表示 | ○ |
| handoff_expires_at | 引継ぎ有効期限 | SPLL | 非表示 | ○ |
| usage_category | 利用目的 | SPLL | ○ | ○ |

| portal_consent_session_id | 同意セッションID | SPLL | 非表示 | ○ |

## 7.2 原作項目

最大5原作の固定枠とする。

```text
work_id_1
work_title_1
work_credit_1
work_id_2
work_title_2
work_credit_2
work_id_3
work_title_3
work_credit_3
work_id_4
work_title_4
work_credit_4

```

空欄の原作枠は、契約書上で空行を生じさせないことが理想である。フォーム・テンプレート機能上の制約により条件表示ができない場合は、空欄を「該当なし」又は「－」として出力する。

reporting_requirement

# 9. 入力規則

## 9.1 共通規則

- 先頭・末尾の空白を除去する
- 改行の連続を制限する
- HTMLタグを無効化する
- 制御文字を除去する
- 契約書差込項目は最大文字数を設定する
- 絵文字及び機種依存文字は原則許容するが、PDF生成結果を事前確認する
- `=`, `+`, `-`, `@`で始まる値をSPLLへ連携する場合は数式無害化する

## 9.2 正規表現例

| 項目 | 規則例 |
|---|---|
| 郵便番号 | `^\d{3}-?\d{4}$` |
| 電話番号 | `^[0-9+()\-\s]{10,20}$` |
| 法人番号 | `^\d{13}$` |
| インボイス登録番号 | `^T\d{13}$` |
| application_ref | `^REF-\d{6}-[A-Z0-9]{6,12}$` |
| 金額 | 0以上の整数 |
| URL | `https://`推奨、必要に応じ`http://`許容 |

## 9.3 日付規則

- 生年月日：未来日不可
- 販売開始予定日：原則として申込日以降
- 既公開開始日：申込日以前も許容
- 不自然な日付はサーバー側又は事務局確認対象とする

# 10. 条件分岐一覧

| 条件 | 表示又は処理 |
|---|---|
| 契約者区分＝個人 | 個人欄を表示、法人欄を非表示 |
| 契約者区分＝個人事業主 | 個人欄＋屋号＋登録番号を表示 |
| 契約者区分＝法人 | 法人欄を表示、個人欄を非表示 |
| 未成年＝はい | 法定代理人欄を表示又は個別対応へ |
| 国内住所＝いいえ | 自動締結を停止し個別対応へ |
| 海外販売＝海外を含む | 対象地域・言語欄を必須化 |
| 利用目的＝RATE | 販売価格・チャネル・報告確認を必須化 |
| 利用目的＝イベント | 開催日・会場項目を追加表示可 |
| 既公開＝はい | 公開開始日・URLを必須化、個別確認フラグ |
| 法人の締結者＝代表者以外 | 権限根拠を必須化 |
| 特約あり | 特約確認チェックを表示 |

# 11. FormRun Webhook取込範囲

SPLLのFormRun Webhook処理では、個人情報をむやみに取り込まない。

## 11.1 原則取り込む項目

- application_ref
- form submission ID又はsequence number
- 送信日時
- フォーム種別
- 受付結果
- handoff token又はterms hash

## 11.2 原則取り込まない項目

- 氏名
- 住所
- 電話番号
- メールアドレス
- 生年月日
- 法定代理人情報

これらはCloudSign/FormRun及び締結済契約PDFに保持し、SPLL台帳には複製しない。

## 11.3 例外

通知、請求又は取引先登録のために個人情報連携が必要な場合は、別途次を定める。

- 利用目的
- 保存先
- アクセス権限
- 保存期間
- 削除方法
- 台帳登録責任者

# 12. CloudSign締結後の検証

Webhook受信後、契約を有効化する前に次を確認する。

| 検証 | 不一致時の状態 |
|---|---|
| 書類IDがCloudSign APIに存在する | RETRY_WAIT |
| 書類状態が締結完了 | RETRY_WAIT又はIGNORED |
| application_refが抽出できる | MANUAL_REVIEW |
| Applicationが存在する | MANUAL_REVIEW |
| Applicationが他契約に使用されていない | DATA_CONFLICT |
| handoff token又はterms hashが一致する | TERMS_MISMATCH |
| 対象原作が一致する | TERMS_MISMATCH |
| 利用目的が一致する | TERMS_MISMATCH |
| 料金・料率が一致する | TERMS_MISMATCH |
| 締結PDFの保存・ハッシュ取得に成功 | SIGNED_PDF_PENDING又はRETRY_WAIT |

`TERMS_MISMATCH`の場合、認証、バッジ、提出トークン、請求を発行しない。

# 13. フォーム完了画面

フォーム送信後の完了画面には、次を表示する。

- 申込受付番号
- CloudSignから署名依頼メールが送信される旨
- メールが届かない場合の確認事項
- 署名完了後に作品提出案内が行われる旨
- 問い合わせ時に受付番号を伝える旨
- フォームを再送信しない旨

表示例：

> お申込みを受け付けました。クラウドサインから電子署名のご案内が送信されます。署名完了後、作品提出に関するご案内を行います。お問い合わせの際は、申込受付番号をお知らせください。

# 14. エラー及び例外時の案内

## 14.1 引継ぎ情報がない場合

> SPLL申込窓口からの引継ぎ情報を確認できません。このフォームを直接開かず、SPLL申込窓口から対象原作及び利用目的を選択してお進みください。

## 14.2 引継ぎ有効期限切れ

> 申込用リンクの有効期限が切れています。SPLL申込窓口からあらためてお申込みください。

## 14.3 海外・未成年・個別条件

> 入力内容について事務局での確認が必要です。この画面では契約を確定せず、事務局から別途ご案内します。

# 15. フォーム作成手順

1. 利用目的又は料金モデルごとのフォーム分割方針を決定する
2. 契約書テンプレートを確定する
3. フォームに表示項目を作成する
4. 契約者区分ごとの条件分岐を設定する
5. hidden項目を作成する
6. FormRunの実項目IDを取得する
7. `FORM_HIDDEN_MAP`へ正規キーとの対応を設定する
8. 契約書テンプレートの差込箇所を対応付ける
9. 完了画面及び自動返信文を設定する
10. FormRun Webhookに共有秘密を設定する
11. CloudSign締結Webhookを設定する
12. ステージングで正常系・改変系・例外系を試験する

# 16. テストケース

## 16.1 正常系

- 個人、原作1件、書籍
- 個人事業主、原作5件、商品販売
- 法人、電子出版物、RATE
- 法人代表者以外の担当者による契約
- イベント無償利用

## 16.2 条件分岐

- 個人から法人へ切替
- 未成年者選択
- 海外販売選択
- 既公開選択
- RATE選択時の報告確認表示

## 16.3 入力検証

- 不正な郵便番号
- 不正な法人番号
- 不正なインボイス登録番号
- メールアドレス不一致
- 負数の販売価格
- 文字数上限超過
- 必須チェック未選択

## 16.4 改変・セキュリティ

- application_ref改変
- work_id改変
- usage_category改変
- 料金改変
- handoff token改変
- 有効期限切れリンク
- 同じApplicationからの二重契約

## 16.5 外部連携

- FormRun Webhook重複
- CloudSign Webhook重複
- CloudSign API障害
- 締結PDF取得失敗
- application_refが契約書タイトルから取得できない

# 17. 受入基準

本フォームは次の条件を満たした時点で受入可能とする。

1. 公開ポータルから遷移した場合に対象原作及び利用条件が表示される
2. 原作及び利用条件をフォーム上で変更できない
3. 個人、個人事業主、法人の入力欄が適切に分岐する
4. 契約者名、住所、代表者等が契約書へ正しく差し込まれる
5. 最大5原作の契約書表示が崩れない
6. 個人情報がSPLL業務台帳へ不要に複製されない
7. 同意文書ID及び申込参照番号を締結後に追跡できる
8. hidden値改変時に自動有効化されない
9. FormRun及びCloudSignの重複Webhookで契約が重複しない
10. 未成年、海外、既公開等の個別確認対象が識別できる
11. 締結済PDFとSPLLの契約条件スナップショットを照合できる
12. 法務、事務局及びシステム担当者がテスト結果を確認している

8. 海外住所・外国語・海外販売を自動受付するか

# 19. 推奨する初期リリース範囲

初期リリースでは、過度な条件分岐を避け、次の範囲に限定することを推奨する。

- 日本国内の成人又は国内法人
- 日本語利用
- 最大5原作
- 利用目的は事前設定済み区分から選択
- 海外販売、外国語、未成年、既公開は個別対応
- 個人情報はCloudSign/FormRun及び契約PDFで管理
- SPLLへはapplication_ref及び契約状態のみ連携

初期リリース後、運用件数及び問い合わせ内容を確認して対象範囲を拡張する。
