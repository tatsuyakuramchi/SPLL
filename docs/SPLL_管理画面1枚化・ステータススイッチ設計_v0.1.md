# SPLL 管理画面1枚化・ステータススイッチ設計 v0.1（たたき台）

**対象:** GAS③ 管理コンソール（`spll_src/admin.html` / `50_admin.gs` ほか）
**作成日:** 2026-11-17
**目的:** 日常業務を「1枚の画面」で完結させる。案件の状態を一覧で見せ、状態の変更は**ステータススイッチ**だけで行う。

---

## 1. 方針

| 現状 | 1枚化後 |
|---|---|
| ダッシュボード／ライセンス／作品審査／認証管理／設定の5タブを行き来する | **案件ボード1枚**。左：状態の集計、中央：案件一覧、右：選んだ案件の詳細とスイッチ |
| 操作ボタンが画面ごとに散らばり、引数が契約ID・申込ID・提出IDでばらばら | 操作はすべて**SPLL番号＋スイッチ名**で呼ぶ（サーバー側で各IDへ解決） |
| 押せない操作も表示され、押した後にエラーで拒否される | 遷移表（`LICENSE_TRANSITIONS`）で**事前検証した結果だけ**をスイッチの「押せる／押せない（理由）」として表示 |
| 設定は日常業務と同じタブ列にある | 設定は右上の歯車から開く**別パネル**（日常業務の画面からは外す） |

状態遷移のルールそのもの（`12_license_state.gs`）は変えない。画面と、画面から呼ぶ入口だけを作り直す。

## 3. ステータス一覧

### 3.1 案件の現在地 `case_status`（左ボードの行）

| 区分 | 値 | 表示名 | 意味 | 次に進める人 | 要対応 |
|---|---|---|---|---|:-:|
| 申込〜別紙 | `APPLICATION_RECEIVED` | 申込受付 | 専用ページで作品を選び、SPLL番号を発行した（別紙の作成・送信待ち） | システム | |
| | `MANUAL_REVIEW` | 個別確認 | 申込の条件が自動送信に載らない／審査の上申 | **事務局** | ⚠ |
| | `SIGNING` | 別紙の同意待ち | 別紙を CloudSign で送信済み。送信から3か月で失効 | クリエーター | |
| | `PAYMENT_PENDING`（新設） | 入金待ち | 前払いの別紙に同意済み。入金CSVの取込で次へ。追加から3か月で失効 | クリエーター／経理 | |
| | `HOLD` | 条件不一致 | 同意された別紙の照合コードが台帳と合わない | **事務局（法務）** | ⚠ |
| 許諾後 | `AWAITING_SUBMISSION` | 提出待ち | 許諾が有効（後払いは同意の時点、前払いは入金確認の時点）、作品の提出待ち | クリエーター | |
| | `REVIEWING` | 審査中 | 提出済み（AI一次審査→人手審査） | **事務局** | ⚠ |
| | `CORRECTION_REQUIRED` | 是正中 | 是正を依頼した | クリエーター | |
| 認証 | `CERTIFIED` | 認証済 | 審査で承認され、認証が有効・バッジ発行済み | — | |
| | `SUSPENDED` | 停止中 | 認証を一時停止中（後払いの支払期限超過など） | 事務局 | |
| 終了 | `TERMINATED` | 終了 | 失効・別紙の取消し・契約終了 | — | |
| | `CANCELLED` | 取消 | 申込取消、別紙の同意期限切れ、前払いの入金期限切れ | — | |

| 軸 | 値 | 記号 |
|---|---|:-:|

| 入金 `payment_status`（新設） | `NOT_REQUIRED`（未請求）/ `UNPAID` / `PAID` / `OVERDUE`（後払いの期限超過） | ○ / ◐ / ● / ! |

| 認証 `certification_status` | `NOT_ISSUED` / `ACTIVE` / `SUSPENDED` / `EXPIRED` / `REVOKED` / `TERMINATED` | ○ / ● / ‖ / ⌛ / ✕ / ✕ |

## 4. ステータススイッチ

### 4.1 考え方

- スイッチ1つが、遷移表のイベント1つ（または1組）に対応する。
- 画面を開いたとき、サーバーが**全スイッチを事前検証**（`validateLicenseTransition_` を書き込みなしで実行）し、
  `enabled`（押せる）／`disabled_reason`（押せない理由）／`needs_approval`（申請が要る）を返す。画面はそれを描くだけ。
  押せないスイッチは灰色にして、理由をツールチップで表示する。
- 押した後の処理は、**既存の業務関数をそのまま呼ぶ**（認証行の更新、バッジ生成ジョブ、メール送信などの副作用がそちらにあるため）。
  `transitionLicenseCase_` を画面から直接呼ぶことはしない。
- 重い変更（失効・契約終了・入金以外の理由の停止／復帰）は、今と同じく**申請→別担当者の承認**とする。
  スイッチは「申請」になり、承認待ちの間は「承認待ち（申請者・日時）」を表示する。

### 4.2 スイッチ一覧

| # | スイッチ | 形 | 遷移イベント | 押せる現在地 | 呼ぶ既存関数 | 承認 | ロール |
|---:|---|---|---|---|---|:-:|---|
| S1 | 別紙を作成して CloudSign で送る | ボタン（送信前にプレビュー） | `CLOUDSIGN_SENT` | 申込受付・個別確認 | 新設：別紙PDFの生成 → `cs_createDocument_` / `cs_attachFile_` / `cs_addParticipant_` / `cs_sendDocument_`（§8）。通常は申込の直後にシステムが自動で行い、S1 は個別確認の後と再送に使う | — | OPERATIONS |
| S11 | 入金CSVを取り込む（画面上部の操作。案件ごとではない） | ファイル選択 → 照合結果の確認 → 反映 | 前払い：新設 `PAYMENT_CONFIRMED`（入金待ち → 提出待ち）／後払い：入金の記録だけ | 入金待ち・後払いの未入金 | 新設（§8.4） | — | OPERATIONS |
| S2 | 条件を確認して有効化 | ボタン | `CLOUDSIGN_SIGNED` | 条件不一致 | `admin_confirmContractTerms(contractId, note)` | — | LEGAL_ADMIN |
| S3 | 審査判定 | 3択（承認／是正／上申） | `HUMAN_REVIEW_CLEARED` / `CORRECTION_REQUIRED` / `REVIEW_ESCALATED` | 審査中・是正中・個別確認・認証済・停止中 | `admin_setHumanReview(submissionId, result, comment, reviewer, versionId)` | — | REVIEWER |
| S4 | 入金未確認で停止 | オン／オフ（2名体制では申請） | `CERTIFICATE_SUSPENDED` ⇄ `CERTIFICATE_RESTORED` | 認証が ACTIVE、またはこの理由で停止中 | `admin_setCertEnabled(contractId, enabled, reason)`（2名体制では `admin_requestCertChange` → `admin_approveCertChange`） | 設定で切替 | OPERATIONS |
| S5 | 一時停止（その他の理由）／復帰 | 申請 | `CERTIFICATE_SUSPENDED` / `CERTIFICATE_RESTORED` | 認証あり | `admin_requestCertChange(...)` → `admin_approveCertChange(...)` | ✔ | LEGAL_ADMIN |
| S6 | 失効 | 申請 | `CERTIFICATE_REVOKED` | 認証あり | 同上（`requestedStatus='REVOKED'`） | ✔ | LEGAL_ADMIN |
| S7 | 別紙の取消し（この作品の許諾だけ終了） | 申請 | `CONTRACT_TERMINATED` | 別紙が本契約に追加済み | 同上（`requestedStatus='TERMINATED'`） | ✔ | LEGAL_ADMIN |
| S10 | 契約の終了（全別紙） | 申請 | `AGREEMENT_TERMINATED` → その契約の全案件に `CONTRACT_TERMINATED` | 契約 ACTIVE | 新設 | ✔ | LEGAL_ADMIN |
| S8 | 失効からの再有効化 | 申請 | `CERTIFICATE_RESTORED` | 契約 SIGNED かつ認証 REVOKED 等 | 同上（`requestedStatus='ACTIVE'`） | ✔ | LEGAL_ADMIN |
| S9 | 申込取消 | ボタン（確認つき） | `APPLICATION_CANCELLED` | 申込受付〜入金待ち（別紙の同意待ちなら CloudSign の書類も取り消す） | `admin_cancelApplication(applicationId, reason)` | — | OPERATIONS |

**スイッチにしないもの**（システムだけが起こす遷移）：`APPLICATION_CREATED`、`CLOUDSIGN_SENT`（自動送信）、`CLOUDSIGN_SIGNED`（別紙への同意）、`MANUAL_REVIEW_REQUIRED`、
`TERMS_MISMATCH`、`SUBMISSION_CREATED`、`CERTIFICATE_ISSUED`（S3 の「承認」から自動で続く）、`APPLICATION_EXPIRED`（新設。同意待ち・入金待ちが3か月を過ぎたら日次バッチで取消）。
画面には履歴として表示するだけにする。

**状態を変えない作業**（スイッチ欄の下に並べる）：専用ページのリンクの再発行、提出リンク発行、バッジ生成ジョブの再試行、照合コードの再発行、再申込（訂正）。

### 4.3 スイッチの見え方

| 状態 | 表示 |
|---|---|
| 押せる | 通常色 |
| 押せない | 灰色＋理由（例：「契約が成立していません（contract_status=SIGNING）」）。遷移表のガード文言をそのまま使う |
| 権限がない | 鍵アイコン＋必要なロール |
| 承認待ち | 「承認待ち：申請者・日時」。申請者本人以外の承認者にだけ［承認］［却下］を表示 |
| 押した直後 | 確認ダイアログ（理由入力が必須のものは入力欄つき）→ 成功したら右パネルと左ボードの件数を再取得 |

## 5. サーバー側に追加するもの

既存の `admin_*` は引数が契約ID・申込ID・提出IDでばらばらなので、SPLL番号で受ける入口を3つ足す。

```js
/** 左ボード＋中央一覧。件数と、絞り込んだ案件の行（4軸の状態・要対応フラグ） */
admin_getCaseBoard({ filter, query, page })
  → { counts: { case_status: n, ... , pending_approvals, mail_failures, inconsistencies },
      rows: [{ license_id, party, case_status, contract_status, review_status,
               certification_status, cert_reason_code, needs_action, updated_at }] }

/** 右パネル。案件の中身と、全スイッチの事前検証結果 */
admin_getCasePanel(licenseId)
  → { license, contract, works, submissions, review, certificate, badge, timeline,
      switches: [{ key:'S3', enabled, disabled_reason, needs_approval, pending_request, required_role }] }

/** スイッチを押す。SPLL番号から各IDを解決して既存関数へ振り分ける */
admin_applySwitch(licenseId, switchKey, params)   // params: { value, reason, note, ... }
  → { ok, panel: admin_getCasePanel(licenseId) の結果 }
```

- 事前検証は `validateLicenseTransition_` に加えて、既存関数が持つ追加条件（職務分離、入金停止の理由一致など）も
  同じ判定を返す関数に切り出して使う。画面で押せたのにサーバーで拒否される、という食い違いを作らないため。
- ロール判定は既存の権限チェックを `admin_applySwitch` の入口でも行う（画面の鍵表示は案内であって、制御はサーバー側）。
- 一覧は `License_Cases` だけを読む（4軸の状態がそろっているため）。認証の理由とバッジの有無だけを `Certificates` / `Badges` から1回まとめて引く。

## 6. 移行の進め方

1. `admin_getCaseBoard` / `admin_getCasePanel` / `admin_applySwitch` を追加し、テスト（`tests/harness.js`）で
   「スイッチの enabled と、実際に押した結果が一致する」ことを全スイッチ・全現在地の組み合わせで確かめる。
2. 新画面 `admin_board.html` を作り、旧画面と並べて置く（`?view=board`）。
3. 運用で問題がなければ既定の画面を新画面に切り替え、旧タブ（ダッシュボード／ライセンス／作品審査／認証管理）を外す。設定は歯車パネルへ移す。

## 7. 決定事項（2026-11-17）

| 論点 | 決定 |
|---|---|
| 事務局運営（会議・議決・報告・精算） | 1枚には入れない。設定と同じ**別パネル**（歯車から開く。タブ「設定」「事務局運営」） |
| S4 入金未確認で停止 | 当面は**担当者1名のスイッチ**。のちに**申請→別担当者の承認（2名体制）**へ移す。切り替えは設定パネルの運用ルール `FEE_HOLD_TWO_PERSON`（Config）で行い、コードの書き換えなしで移行できるようにする |
| 契約の構成 | **利用許諾契約＋別紙**（§8）。①利用許諾契約（全利用区分の利用条件・料金の決め方・振込先）を初回に formrun（CloudSign FORM）→ CloudSign で締結。作品はまだ選ばない。②登録メールへ専用ページのリンクを送り、そこで作品を選ぶと、SPLL が別紙（契約番号入り）を作って **CloudSign API で送信し、同意で本契約に追加**する。名称は「基本契約／個別契約」から「利用許諾契約／別紙」に改めた |
| 専用ページ | **トークン式**（ログインなし）。利用許諾契約で登録したメール宛てに長期の入口リンクを送る。今の案内ページを広げて作る |
| 支払方法 | **利用区分で決める**（料金表に前払い／後払いの列を足す）。前払い：入金確認で許諾が有効、そのあと提出。後払い：同意の時点で許諾が有効、すぐ提出できる |
| 入金の確認 | **入金CSVの取込**（経理から受け取る）。前払いは取込で入金待ち → 提出待ちへ進む。後払いは入金を記録し、支払期限を過ぎて未入金なら要対応に出す（止めるのは S4） |
| 期限 | 別紙の同意待ち・前払いの入金待ちとも **3か月**。過ぎたら日次バッチで取消（`APPLICATION_EXPIRED`） |
| 認証バッジ | 支払方法にかかわらず **審査で承認された後** に発行（利用許諾契約書第8条第5項）。今のルールのまま |
| 契約の相手方 | **各パートナーが当事者**（SPLLパートナーシップのクロスライセンスに合わせる）。当事者表記は「SPLL事業TRPG事務局代表法人株式会社アークライト」に固定し、代表法人が各パートナーを代表して締結・別紙の送信・利用許諾料の受領を行う。別紙の対象作品は、その作品の権利者パートナーが許諾する。各パートナーは当事者として権利を自ら行使できる。パートナー一覧は公開ページで版管理し、加入時から当事者に加わる。脱退したパートナーの作品の許諾は別紙の許諾期間満了まで続く（利用許諾契約書 前文・第4条・第6条第9項） |
| 入口と処理の分担 | **サイトは AWS（CloudFront + S3、中継は Lambda）で入口だけ**。処理はすべて GAS。利用許諾契約は formrun → CloudSign で結び、**CloudSign の締結 Webhook で回収した情報を GAS の台帳のもとにする**（§10） |
| アクセス集中への備え | 入口では GAS を呼ばない。Webhook と専用ページの申込は「受信・受付の記録だけ」にして、重い処理は1分ごとの定期実行に回す（§10.5） |

未決：一覧の既定の絞り込み（モックは「要対応」）。

## 8. 契約の構成（利用許諾契約＋別紙）

### 8.1 契約の構成

| | 利用許諾契約（本契約） | 別紙（許諾作品通知書） |
|---|---|---|
| 単位 | クリエーター1人につき1本（契約番号） | 作品1本ごと（SPLL番号）。数の上限なし |
| 中身 | 当事者（氏名・住所・メール）、全利用区分の共通条件、料金の決め方（申込時の料金表）、前払い／後払いの扱い、振込先、別紙の追加方法、認証は審査後 | 契約番号、対象作品（表・行数の上限なし）、利用区分、許諾期間、利用許諾料、支払方法、支払期限、利用報告、権利表記、特約 |
| 作る人 | クラウドサインのテンプレート（固定文面）。formrun が当事者欄を差し込む | SPLL が台帳（申込時に確定した条件）から PDF を作る |
| 送り方・成立 | サイト → formrun → CloudSign。同意で成立 | CloudSign API で送信。**同意で本契約に追加**。送信から3か月で失効 |
| 個人情報 | formrun で入力。SPLL が受け取るのは氏名・メール（今と同じ） | 氏名・契約番号・送信先メールだけ。住所・振込先は載せない |
| 正本 | `docs/SPLL_利用許諾契約書_v5.0.md` | `docs/SPLL_別紙_許諾作品通知書_v1.0.md` |

サンプルPDF（利用許諾契約書、別紙 3作品・前払い／25作品・後払い）は `docs/contract/`。組み立ては `docs/contract/build_contract.js`。

### 8.2 流れ

```
① サイト（AWS）で受付番号を発行 → formrun で契約情報を入力 → CloudSign で利用許諾契約に同意
   → 締結 Webhook（AWS で中継）→ GAS が受信表に記録 → 定期実行で書類を確認し契約番号を発行（§10）
② 登録メールへ専用ページ（トークン式）のリンクを送る
③ 専用ページで作品を選んで申込 → SPLL番号を発行・条件を確定（APPLICATION_RECEIVED）
④ 別紙PDFを作成（契約番号入り）→ CloudSign API で送信（CLOUDSIGN_SENT → SIGNING）
   └ 3か月同意がなければ取消（APPLICATION_EXPIRED → CANCELLED）
⑤ 別紙に同意 → 締結 Webhook → 照合コードを確認 → 本契約に追加（CLOUDSIGN_SIGNED）
     後払い：許諾が有効 → AWAITING_SUBMISSION
     前払い：PAYMENT_PENDING → 入金CSVの取込で PAYMENT_CONFIRMED → AWAITING_SUBMISSION
             └ 3か月入金がなければ取消（APPLICATION_EXPIRED → CANCELLED）
⑥ 専用ページから作品を提出 → AI一次審査 → 人手審査（REVIEWING）
⑦ 承認 → 認証を有効にし、バッジを発行（CERTIFIED）
   後払いで支払期限を過ぎて未入金 → 要対応に表示 → 事務局が S4 で一時停止
```

- 個別確認（`MANUAL_REVIEW`）に回った申込は、事務局の確認後に S1 で別紙を送る。
- 別紙の作成と送信は申込の処理と切り離し、即時起動のトリガーか5分バッチで行う。専用ページの完了表示は「クラウドサインから別紙をお送りします」。
- 申込から送信までに原作マスタや料金表が変わっても、別紙は申込時に確定した内容で作る。
- 専用ページのリンクは本人専用（利用許諾契約書第3条第7項）。期限切れ・紛失時は管理画面から再発行する。

### 8.3 これで不要になるもの

- formrun の URL 長の検査（`FORM_URL_MAX_CHARS`）と、3作品を超えたら個別確認に回す処理。
- 作品名・金額・権利表記を formrun の hidden 項目で運ぶこと（`FORM_HIDDEN_MAP_*` は当事者欄と照合用の項目だけになる）。
- 最初の申込で作品を選ばせること（利用許諾契約の段階では作品を選ばない）。

### 8.4 システムへの影響

- 台帳：`Agreements`（契約番号・氏名・メール・CloudSign 書類ID・版・状態・締結日時）を新設。`License_Cases` に `agreement_no`、別紙の CloudSign 書類ID・PDFのファイルID・照合コード・送信日時・同意日時、`payment_timing` / `payment_status` / `payment_due` / `paid_at` を足す。
- 料金表（`Fee_Schedule`）：利用区分ごとに `payment_timing`（PREPAID / POSTPAID）を足す。
- 状態遷移：契約側に `AGREEMENT_SIGNED` / `AGREEMENT_TERMINATED`。案件側に `PAYMENT_PENDING` 状態と `PAYMENT_CONFIRMED` / `APPLICATION_EXPIRED` イベントを新設。`CLOUDSIGN_SIGNED` は、前払いなら `PAYMENT_PENDING`、後払いなら `AWAITING_SUBMISSION` へ進める。`SUBMISSION_CREATED` は許諾が有効な案件（`AWAITING_SUBMISSION` 以降）でだけ受け付ける。契約の終了で、その契約の全案件に `CONTRACT_TERMINATED`。
- 締結 Webhook：書類IDで「利用許諾契約」か「別紙」かを振り分ける。
- 入金CSVの取込（S11）：取込 → 照合結果の確認 → 反映 の3段。照合キーは振込名義に入れてもらう **SPLL番号**（別紙と案内メールで「振込名義の前に SPLL番号を付けてください」と案内）と金額。照合できない行・金額が合わない行は反映せず、要対応に「未照合の入金」として残す。同じCSVを2回取り込んでも二重に反映しない（行のハッシュで判定）。取込の記録は `Payment_Imports` / `Payments` に残す。
- 日次バッチ：同意待ち・入金待ちが3か月を過ぎた案件を取消（CloudSign の書類も取り消す）。後払いの支払期限超過を `OVERDUE` にして要対応に出す。
- 専用ページ：`Access_Tokens` に用途 `MY_PAGE`（長期・本人の登録メールにだけ送る）を足す。今の案内ページ（`44_guide.gs` / `guide.html`）に「新しく申し込む（作品を選ぶ）」「別紙と状態の一覧」「作品の提出」を集める。
- 管理画面：案件の詳細に「利用許諾契約」「別紙（同意・入金）」欄を足す。S1 は別紙の送信、S10（契約の終了・承認制）、S11（入金CSVの取込）を追加。
- 確認が要ること：CloudSign のプランで API 送信が使えるか。経理から受け取る入金CSVの列（日付・金額・振込名義など）。

## 9. モック

`docs/SPLL_管理画面1枚化モック_v0.1.html`（サンプルデータで操作できる）。操作者の切り替えで権限と職務分離、

## 10. 入口の設計とアクセス集中への備え

### 10.1 役割分担

```
クリエーター
  │
AWS（入口だけ）
  ├ CloudFront + S3 …… 画面（申込の入口・専用ページ・提出・検証）。作品一覧のデータは5分キャッシュ
  └ Lambda（関数URL）…… GAS への中継（共有鍵を付ける）、トークン単位の回数制限、
                          受付番号の発行、CloudSign / formrun の Webhook の中継（GAS の 302 対策）
  │
formrun（クラウドサインフォーム）→ CloudSign …… 契約者情報の入力と利用許諾契約の締結
  │ 締結 Webhook
GAS（処理はすべてここ）
  ├ すぐ返す処理 …… Webhook の受信記録、専用ページの表示内容、作品選択の受付（受付表に1行足すだけ）
  └ 定期実行（1分ごと）…… 契約の作成・専用ページのリンク送信、SPLL番号の採番・別紙PDFの作成・CloudSign 送信、メール
```

- 今の Cloud Run の中継処理（`apps/public-web/server.js`）は Node.js のまま Lambda に移す。
- GAS を入口に直接出さない理由：共有鍵をブラウザに置けない。GAS は POST に 302 を返すため、追わない送信側が失敗する。

### 10.2 利用許諾契約までの流れ（GAS のベースは CloudSign の締結書類）

1. サイトの入口で、Lambda が受付番号（推測できない乱数）を発行し、formrun の hidden 項目に入れて遷移させる。**GAS は呼ばない。**
2. formrun で契約者情報を入力し、CloudSign で利用許諾契約に同意する。
3. CloudSign の締結 Webhook を Lambda が中継し、GAS は `Webhook_Receipts` に1行記録して直ちに 200 を返す（業務処理はしない）。
4. 1分ごとの定期実行が受信行を処理する：CloudSign API で書類を取り直して締結を確かめる → 受付番号でひも付け → 契約番号を発行して `Agreements` を作る → `MY_PAGE` トークンを発行 → 登録メールへ専用ページのリンクを送る。
5. 台帳のもとは formrun の入力値ではなく **CloudSign の締結書類**（送信先メールアドレス・締結済みPDF）。住所は持たない。
6. formrun の Webhook は「フォーム送信済み」の補助記録だけにし、無くても契約は作れるようにする。
7. **取りこぼしの照合**：1日数回、CloudSign API で締結済み書類の一覧を取り、台帳に無いものを拾う。中継口は GAS の応答を待たずに送信元へ 200 を返すため、GAS 側で受け損ねた通知は送信元から再送されない。照合はその備え。

### 10.3 専用ページの流れ

1. 作品の検索・選択はブラウザの中で完結させる（作品一覧は CloudFront のキャッシュ。検索のたびに GAS を呼ばない）。
2. 申込は受付表（`Apply_Queue`）に1行足して返すだけ。ロックは使わない。
3. 定期実行が、SPLL番号の採番 → 条件の確定 → 別紙PDF → CloudSign API 送信を1件ずつ順に行う。採番のロック待ちは起きない。
4. PDF は GAS で作る。第一候補は HTML → PDF 変換（1件 2〜3秒の見込み）。表の見出しの繰り返しなど、見た目が再現できなければ Google ドキュメントのひな形に行を足す方法（1件 5〜10秒、作成は1日1,500件まで）。

### 10.4 GAS の上限と危うくなる目安

前提（Google Workspace のアカウント・公式の上限）：同時に動ける実行は**デプロイしたアカウント1人あたり30**（3つの GAS・定期実行・Webhook の合計）、外部 API 呼び出し 1日10万回、メール 1日1,500通、1回の実行 6分、定期実行の合計 1日6時間。
30 のうち 5 は定期実行・Webhook・管理画面の分として、25 を使える分として計算する。同時実行の数 ＝ 1秒あたりの件数 × 処理時間。処理時間は推定（本番前に負荷試験で置き換える）。

| 詰まる箇所 | 計算 | 危うくなる目安 |
|---|---|---|
| 入口〜利用許諾契約の締結 | GAS は0回 | formrun・CloudSign 側の容量次第 |
| Webhook の受信（約0.5秒） | 25 ÷ 0.5秒 | 毎秒数十件まで受けられる。先にスプレッドシートへの同時書き込みが限界（**毎秒5〜10件**） |
| 契約の作成（定期実行・1件約4秒） | 1回50秒で約12件 → 1時間 約720件 | 遅れるだけ。**1時間に700件を超える締結が続くと、専用ページのリンクが届くまで1時間を超える** |
| 専用ページの表示・受付（約2秒／約0.7秒） | 25 ÷ 平均約1.5秒 ≒ 毎秒15回 | **GAS への呼び出しが毎秒10回（1分 600回）を続けて超えるあたり** |
| 受付表への同時書き込み | 同じ表への同時追記 | **毎秒5〜10件（1分 300〜600件）** |
| 別紙の作成・送信（定期実行・1件約6秒） | 1回50秒で約8件 → 1時間 約480件 | 遅れるだけ。**1時間に500件を超える申込があると別紙が届くまで1時間以上**。定期実行を3本並べれば約3倍 |
| 定期実行の1日の合計（6時間） | 21,600秒 ÷ 6秒 | 別紙 1日 約3,600件 |
| メール（1日1,500通） | 1件につき2〜3通 | **1日 約500〜700件**（1日の上限で最初に来る） |
| データの量 | 読むたびに表全体を読む。案件が数千件になると表示が5秒以上に延び、上の数字が下がる | 案件1万件の手前で読み方の見直し（索引・キャッシュ） |

参考：今の作り（すべて同期・採番にロック）のままだと、**申込 1分 約40件**でロック待ちが伸び始め、告知直後10分に1,000人が来ると失敗が続出する。安全なのは10分で300人程度まで。

### 10.5 備えの一覧

1. 入口では GAS を呼ばない（受付番号は AWS で発行）。
2. Webhook は受信記録だけ返し、処理は定期実行（`receiveWebhook_` の同期処理を止める）。
3. 専用ページの申込は受付表に記録するだけ。採番・別紙・送信は定期実行。
4. 作品の検索・選択はブラウザの中（一覧は CloudFront のキャッシュ）。
5. 3つの GAS を別々のアカウントでデプロイし、同時実行の枠を分ける。
6. 回数制限は AWS 側でトークン単位（IP 単位は共有回線で誤ってまとめて止めるため使わない）。
7. メールは最小限（別紙の通知は CloudSign のメールに任せる）。
8. CloudSign の締結書類の照合バッチで、通知の取りこぼしを拾う。
9. 本番前に負荷試験（10分に1,000人の想定）で、上の推定を実測に置き換える。

# 付録：CloudSign FORM で「作品数の上限なし」にできるか

## 結論

**今の方式（formrun の初期値つきURLで条件を渡し、CloudSign のテンプレートに差し込む）では、上限なしにはできない。**
制約は2か所にある。

| 箇所 | 制約 | 根拠 |
|---|---|---|
| ① フォームへの受け渡し | 初期値つき公開フォームURLは**1000文字まで**。超えるとエラーページになる | formrun 公式FAQ「フォームに初期値を設定する方法」 |
| ② 契約書のレイアウト | CloudSign のテンプレートは**決まったPDFの上に入力欄を置く**方式。欄は文字量に応じて伸びず、ページも増えない。1行おおむね60字で自動改行し、フォントの変更はできない（大きさの扱いはヘルプ間で記述が分かれる） | クラウドサイン ヘルプ（テキストの改行、フォント・サイズ） |

いまの実装では①により、URLの安全上限を850字（`FORM_URL_MAX_CHARS`）に置き、**実測で3作品まで**が自動締結の対象になっている
（`docs/SPLL_CloudSign_FORM_実装仕様_v2.1.md` §4）。`FORM_MAX_WORKS` は5だが、URL長の検査が先に効く。

## ① 受け渡しの上限は外せる見込みがある

formrun の「コード型フォーム」（自前のHTMLから formrun へPOSTする形式）は、クラウドサイン連携の対象と案内されている。
URLに値を載せないため1000字の制約がなくなり、1行テキストは10,000字まで入る。
公開サイト（Cloud Run）からPOSTすれば、作品数を増やしても受け渡しはできる。

ただし次は**実機で確認が要る**：コード型フォームで hidden 項目がクラウドサインの差込欄に紐づけられるか、
2024年7月の「クリエイターフォームでのコード型フォーム併用の廃止」が今の構成に影響しないか。

## ② 契約書の差し込みは、テンプレート方式のままでは上限が残る

受け渡しの上限を外しても、テンプレート上の欄の大きさは決まっている。

- **作品名を1つの欄に連結する方式（現行）**：欄の高さを超えた分は表示されない（または欄からはみ出す）。何作品まで入るかは欄の大きさと作品名の長さで決まり、固定の上限にはならないが、無制限にもならない。
- **作品ごとに欄を並べる方式**（`work_title_1`〜`_N`）：上限は欄の数Nになる。

## 上限なしにするための選択肢

| 案 | 内容 | 作品数 | 主な手間・リスク |
|---|---|---|---|
| A. 別紙目録で特定する | 契約書には「対象作品：SPLL番号○○に係る別紙目録記載のとおり（計N作品・目録ハッシュ××）」とだけ差し込み、目録は締結前に公開サイトで提示し、締結後は検証ページで公開する | 無制限 | 目録が契約書PDFの外にある。**法務の判断が要る**（契約書だけで原著作物を特定できない） |
| B. CloudSign API で直接送る | 作品数に合わせた契約書PDFをGAS（Googleドキュメントのひな形→PDF）で作り、CloudSign API で送付する。`30_cloudsign.gs` に書類作成・PDF添付・送付の関数（`cs_createDocument_` / `cs_attachFile_` / `cs_sendDocument_`）がすでにある | 無制限（ページが伸びる） | PDF生成と送付処理の実装。フォーム画面は公開サイトの申込ウィザードが担う。CloudSign API が使えるプランかの確認 |
| C. 現行のまま | 3作品を超える申込は個別確認（`MANUAL_REVIEW`）へ回す | 3程度 | 4作品以上は事務局の手作業 |

**推奨は B。** ※最終的には、利用許諾契約を formrun 経由で締結し、作品ごとの条件は別紙をメールで送って本契約に追加する構成を採用した（本文 §8）。 1ライセンス＝1作品で、1作品が複数の原作を使う形なので、「対象原作」は契約の中核であり、契約書PDFの中に全件を載せるべき。
B なら formrun の1000字制約とテンプレートの欄の大きさの両方から外れる。締結の Webhook（`35_webhooks.gs` の CloudSign 受信）と
条件の改変検知（スナップショットのハッシュ）はそのまま使える。
B に移るまでの間は C を続け、必要ならコード型フォームで①だけを外して上限を3から数件増やす。
